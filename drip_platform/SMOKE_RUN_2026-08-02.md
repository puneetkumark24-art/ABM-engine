## The run found a real bug

**Step 4 failed on the first attempt**: `campaign_status=sent` when it should
have been `awaiting_approval`. The campaign was being marked complete while an
executive draft was still sitting in the approval queue — precisely inverting the
guarantee that branch exists to provide, and one of the headline items in the v4
audit.

Cause: `SessionLocal` is built with `autoflush=False` (`database.py`).
`send_campaign()` adds the c-suite approval `Draft`, then counts pending
approvals to decide the campaign's status. Without a flush the new Draft is
still only in the identity map, so the count returns 0. Fixed with a `db.flush()`
before the count.

The existing test suite did not catch it because it asserted on
`held_for_human`/`sent` in the return value, never on the campaign's status. It
now asserts the gate explicitly in both directions, on the persisted row — and
the assertion was verified to actually catch the bug by removing the fix and
watching it go red.

**This is the argument for running software rather than only testing it.** The
unit path, the merge review and the candidate's own audit all passed this code.
One end-to-end run through the API surfaced it in the first minute.

## Also fixed during the run

Four checks in `test_unified` asserted exact **global** counts (executive
dashboard accounts/contacts, growth-operations flow totals, email analytics).
That module's `drop_all()` runs at import, so under `pytest tests/` it fires
during collection — before any other suite's test function has run — and rows
created afterwards by earlier-collected suites were still present. Reproduced on
the pre-v4 baseline, so long-standing. Email totals are now scoped to the
campaign under test; the count checks assert the join and the contactability
filter instead of an absolute.

Moving the reset into `run()` was tried first and **rejected**: an earlier
suite's still-open session holds locks that `DROP TABLE` then waits on, which
hangs the run. Worth knowing before anyone tries the same tidy-looking fix.

## Running it on your machine

The sandbox run above is a Linux copy against a throwaway database — it does not
start anything on your PC. To run the real thing:

```
double-click:  Start DRIP Platform.bat      (in drip_platform\)
then open:     http://127.0.0.1:8000/
```

That binds to `127.0.0.1` only. One thing to check first: `alembic upgrade head`
should be run against your PostgreSQL, since the launcher calls `sync_db.py`
rather than Alembic and production schema changes are Alembic's job now. This
merge added no migration, so if you were current before, you are current now.
